# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A multi-user file hosting/sharing tool. Users log in (accounts live in the `users` table; the first account, id=1, created via the first-run welcome page, is the super admin — registration of further accounts is a config toggle), upload files or write them in the dashboard's new-file modal — `.html` (served verbatim), `.md`/`.markdown` (rendered to HTML), or `.txt` (shown as HTML-escaped preformatted text) — stored as text in SQLite, never on disk, and marks each one public or private. A file's format is recorded in its `kind` column (`html`/`markdown`/`txt`) and fixed at creation; the raw source of every kind lives in the `html_content` column regardless. Public files are viewable by anyone with the file's access code (`/res/{slug}?code=...`); private files require an active session. It's a monorepo: a Go API backend and a SvelteKit SPA frontend, built as a single deployable binary/container.

## Commands

Run everything from the repo root via the `Makefile` (each target just `cd`s into `backend/` or `web/`):

```
make dev-api      # go run ./cmd/server (backend on :8080; reads/creates data/app.db — no credential env vars, the first user is created on the welcome page)
make dev-web      # pnpm run dev (Vite dev server on :5173, proxies /api and /res to :8080)
make build-web    # pnpm run build, then copies web/build/* into backend/internal/web/dist
make build-api    # go build -o bin/server ./cmd/server
make build        # build-web + build-api (produces a single self-contained binary)
make check        # frontend: pnpm lint (prettier + eslint) then svelte-check; backend: gofmt -l then go vet
                  # Must stay a superset of .github/workflows/ci.yml. It omitted lint, so a contributor
                  # could get `make check` green -- which the README calls the bar -- and still fail CI.
make sqlc         # regenerate backend/internal/db/sqlcgen from queries + migrations
make test         # frontend vitest + backend go test
make tidy         # go mod tidy
```

For local full-stack dev, run `make dev-api` and `make dev-web` in separate terminals — the Vite dev server proxies API/backend routes so the frontend never needs CORS handling.

To run a single test:
- Backend: `cd backend && go test ./internal/auth/... -run TestName`
- Frontend: `cd web && pnpm exec vitest run src/lib/schemas/login.spec.ts` (or `-t "test name"`)

Frontend-only commands (run from `web/`): `pnpm run lint` (prettier --check + eslint), `pnpm run format` (prettier --write).

Docker: `docker compose up -d` pulls the published image and starts it bound to `127.0.0.1:8080`, expecting an Nginx reverse proxy in front in production. To build the image locally instead: `docker build -t renderbin:dev .`.

## Architecture

**Single-binary deployment model.** The frontend is a static SvelteKit SPA build; `make build-web` copies its output into `backend/internal/web/dist`, which is embedded into the Go binary via `//go:embed` (`backend/internal/web/web.go`). The compiled server serves both the API and the static frontend — there is no separate frontend server in production. Nothing under `backend/internal/web/dist/` is tracked except its `.gitignore` -- that one file is enough for `//go:embed all:dist` to compile on a fresh clone (the SPA 404s until you run `make build-web`, which is the honest outcome). It used to track `index.html` as a "placeholder", but `make build-web` overwrote it with real, hash-referencing build output, so every frontend build dirtied a tracked file and a fresh clone produced a binary serving a page whose assets 404.

**Backend layout** (`backend/`, module `github.com/shawn-bluce/renderbin/backend`):
- `cmd/server/main.go` — entrypoint; wires config (`LISTEN_ADDR` and `DB_PATH` via `envOr`; `MAX_FILE_SIZE_MB` and `PUBLIC_SHARE_BASE_URL` via `internal/config` — all defaulted, with invalid size/origin values failing startup; there are **no credential env vars**; accounts live in the `users` table), opens the DB, builds the router, starts `http.ListenAndServe`. `cli.go` handles subcommands *before* that: a bare invocation still starts the server (the container's ENTRYPOINT depends on it, and `TestNoArgsRunsTheServer` pins it), while `--help`/`--version` and `reset-password --user=NAME` are handled and exit. `reset-password` exists for the one lockout the app cannot fix from inside: the super admin can reset anyone else's password from Settings, but nothing can reset *theirs*, and there is no email recovery by design — so the alternative was editing SQLite by hand. It reads the new password from stdin unless `--password` is given, opens the same `DB_PATH` (safe against a running server, thanks to WAL plus `busy_timeout`), and ends that account's sessions like the HTTP reset does.
- `internal/db/` — `db.go` opens the SQLite connection (via `modernc.org/sqlite`, pure Go, no CGO, DSN `_time_format=sqlite&_timezone=UTC` — see **Timestamps**), enables WAL mode, and runs a hand-rolled migration runner: it reads `internal/db/migrations/*.sql` (embedded), applies any file not yet recorded in a `schema_migrations` table, in filename sort order, each in its own transaction. Add new schema changes as a new numbered file (e.g. `0003_*.sql`), never edit an already-applied one. `0001_init.sql` is the whole schema: the seven incremental migrations that predated the first release were squashed into it, verified by regenerating `sqlcgen` from both the old and the squashed set and diffing (byte-identical). It preserves the column order those ALTER TABLEs produced, which is why `files` reads oddly -- `deleted_at` mid-table, `kind` near the end. The one intentional change was dropping `DEFAULT 1` from `files.user_id` and `sessions.user_id`: that default was a backfill artifact, and a silent fallback owner is worse than a NOT NULL failure. `0002_accounts_expiry_reason_timestamps.sql` adds `users.disabled_at`, `files.expired_at`/`expired_reason`, and rewrites the timestamps an earlier build stored in Go's own format (see **Timestamps** below). `0003_content_size_quota_indexes.sql` adds `files.content_size` (backfilled with `length(CAST(html_content AS BLOB))` — bytes, not characters) and `users.quota_bytes` (default 100MB), and adds the index every owner-scoped query always wanted, `files(user_id, deleted_at, created_at)`, plus `sessions(user_id)`; it drops the superseded `idx_files_list`. `internal/db/queries/*.sql` holds sqlc query annotations; `internal/db/sqlcgen/` is **generated** (`make sqlc`) — don't hand-edit it. There's no ORM by design.
  - `files.sql` is split into two banner-marked sections. Everything in **OWNER-SCOPED** carries `user_id = sqlc.arg(user_id)`; new file queries go there and must carry it. The **UNSCOPED** section exists only for the anonymous `/res/{slug}` render path (`GetFileBySlugAnyOwner` plus the counter bumps and `ExpireFile`) — the name says the hazard, and nothing behind `requireAuth` may call it. `GetFileBySlugAnyOwner` joins `users` and filters `disabled_at IS NULL`, which is how account suspension takes a user's share links offline: a suspended owner's file matches no row and gets the same 404 as a slug that never existed. `HardDeleteUserTrash` is the only unbounded delete in the **OWNER-SCOPED** section; its `deleted_at IS NOT NULL` predicate is the whole safety property. A third **ADMIN CASCADE** section holds exactly one query, `DeleteUserFiles`, used only by account deletion: it carries `user_id` like everything above it, but the id is the *target account's*, so the owner-scoping argument does not protect it and it has no `deleted_at` guard either — only `AdminHandler.Delete`'s super-admin check stands between it and every file an account owns.
  - **The two listings and the name search do not select `html_content`, and must not start.** They were `SELECT *`, so the handler pulled every document's full source out of SQLite only to blank the field before encoding: an account holding 160MB of files drove the server to 350MB RSS to answer a 13KB list request (measured; it is 68MB now). They select an explicit column list plus `content_size` instead, which is why sqlc emits a `...Row` struct for each and `files.go` has four small converters back into `sqlcgen.File`. Content search returns a `substr()` window around the match rather than the document, for the same reason. `GetUserFileBySlug` is the one endpoint that returns content, and it returns one row.
  - **`content_size` is written by the INSERT and UPDATE statements themselves** (`length(CAST(sqlc.arg(html_content) AS BLOB))`), not by Go, so there is no way to write the content without writing its size in the same statement.
  - **Keep the query files pure ASCII.** sqlc's SQLite rewriter substitutes parameters by byte offset while the parser reports character positions, so a single multi-byte character in a comment silently corrupts codegen — you get parse errors about mangled tokens like `SELid` or `nam?1` pointing at innocent lines.
- `internal/auth/` — pure, DB-free credential/token/cookie mechanics: `HashPassword`/`VerifyPassword` (bcrypt, for `users.password_hash`), `ValidatePassword` (the single statement of the password rules, used by setup, registration, the profile page, the admin reset and the CLI — it enforces `MinPasswordLen` **and** bcrypt's own 72-*byte* ceiling, which nothing checked before, so a perfectly ordinary 25-character Chinese passphrase is 75 bytes and came back as HTTP 500 "internal error" on the app's very first screen), `NewGeneratedPassword` (16 characters from an alphabet with no 0/O/1/l/I, for accounts the super admin creates on someone's behalf), `BurnPasswordCheck` (spends one bcrypt compare when the username doesn't exist, so login timing doesn't leak username existence), `NewSessionToken`/`NewAccessCode`/`NewAPIKey` (crypto/rand; API keys are `rb_` + 48 hex chars), `SetSessionCookie`/`ClearSessionCookie` (`rb_session`, HttpOnly/SameSite=Lax, explicit `Expires`/`MaxAge` matching `SessionTTL` = 30 days). **`Secure` is a parameter, not a constant** — callers pass `handlers.requestIsSecure(r)`. It used to be hardcoded true, which made self-hosting over `http://<lan-ip>` look like a rejected password: the login succeeded, the browser silently discarded the Secure cookie (only localhost is exempt), and the next request bounced back to `/login` with nothing to show. Deriving it from the request cannot weaken an HTTPS deployment, since the flag is set wherever the scheme is https.
- `internal/handlers/` — HTTP handlers, one file per resource: `auth.go` (login/register/logout/me; registration is gated on the `allow_registration` config and auto-logs the new user in; a suspended account gets 403 *after* its password verifies, so the message reaches its owner without becoming a username oracle), `setup.go` (first-run status + super-admin creation, only valid while the users table is empty), `settings.go` (global configs — readable by any logged-in user, writable only by the super admin (id=1, `IsSuperAdmin`) — plus profile nickname/password updates, `GET /api/user/usage` (the caller's stored bytes and quota; its own endpoint rather than a field on `/api/auth/me`, which the layout guard hits on every navigation), and the per-user MCP API key ensure/reset), `admin.go` (account management, super admin only: list, **create** — the server generates the password and returns it once, since opening global self-registration to add one colleague was the previous workaround — suspend/restore, reset another account's password, set a storage quota, and **delete**, which hard-deletes the account's files and sessions with it in one transaction because rows owned by a vanished id are invisible to every listing and unremovable through the app), `backup.go`, `mcp.go` (the MCP server, see below), plus `session.go` holding the identity helpers (`CurrentUser`/`CurrentIdentity` — session cookie first, then Bearer API key — `WithIdentity`, `requireUser`, `requireSuperAdmin`), `json.go` holding `decodeJSON`/`decodeSmallJSON`/`writeJSON` (see **Request bodies** below), `request.go` holding `requestIsSecure`/`requestBaseURL` (the two things every handler needs to know about how a request reached us, both `X-Forwarded-Proto`-aware), and `content.go` holding the kind constants (`KindHTML`/`KindMarkdown`/`KindText`) and the `renderContent` logic that turns a file's stored source into the bytes served by `Render` (html verbatim; markdown via goldmark into a styled, self-contained page; txt HTML-escaped inside a `white-space: pre-wrap` `<pre>`). Markdown runs goldmark with GFM **and raw-HTML passthrough enabled** — deliberate, since the `html` kind already serves uploader-authored HTML verbatim, so uploaders are trusted authors and sanitizing markdown would buy no safety that kind doesn't already give away. Handlers take the generated `*sqlcgen.Queries` and a `*slog.Logger` (plus the `*sql.DB` where a transaction is needed: `backup.go`, and `admin.go` for the delete cascade).

  **Request bodies.** Every handler that decodes JSON goes through `decodeSmallJSON` (64KB) or `decodeJSON` with an explicit limit; none calls `json.NewDecoder(r.Body).Decode` directly, and new ones must not. `encoding/json` buffers the whole top-level value before decoding, so an uncapped decode makes the request body the heap — one unauthenticated `POST /api/auth/login` with a 64MB body took the server from 21MB to 423MB of RSS (measured; it is 25MB now). The two file endpoints use `maxFileBody(configuredBytes)`, which is `2*configuredBytes + 64KB` rather than a snug margin: the body is JSON, escaping costs a byte per quote/backslash/newline, and the old snug cap meant a legal document tripped the reader before the decoder ran and came back as 400 "invalid request body". Oversize is 413 with a distinct, dynamically sized message, so "too big" never reads as "malformed".

  **Quota.** `enforceQuota` rejects a create or update that would push the owner's `SUM(content_size)` past `users.quota_bytes`. **Every path that stores content calls it** — `FilesHandler.checkQuota` wraps it for HTTP (413), and MCP's `createUpload`/`updateFile` call it directly; a limit one protocol ignores is not a limit, and an API key was briefly able to store 206KB against a 4KB quota. It (default 100MB, per account, settable by the super admin). It sums the column, not the documents, so it costs an indexed aggregate. Trashed rows count: they still occupy the database, and emptying the trash is a user action, so excluding them would make soft-delete an unlimited bypass. An edit subtracts the row it replaces (`GetUserFileSize`) so an in-place rewrite is not charged twice. It is a check-then-write, so two simultaneous uploads can overshoot by one file -- an accepted rounding error on a limit meant to stop a runaway account, not to bill anyone. Config keys (`allow_registration`, `mcp_enabled`, `upload_default_public`) are defined in `auth.go`; boolean configs store `"true"`/`"false"` in the `configs` table and read as false when missing. `upload_default_public` sets the visibility a new file starts with on the HTTP create path (missing = private, the fail-closed direction); it is deliberately not a create-request field — visibility changes are their own endpoint — and MCP uploads ignore it, since the upload tools promise "starts private" and `publish_file` is the agent's explicit consent step (`TestUploadDefaultVisibilityConfig` pins all three halves). `files.go` also holds `parseExpiryLimit`, the single validator for the "ttl and max_views are mutually exclusive" rule, and `ttlDeadline`, the ttl grammar — `<positive integer><unit>` with unit `h`/`d`/`w`/`mo`/`y`, capped at 10 years (`999999y` would otherwise overflow `time.Time` into a deadline in the *past*), where `mo`/`y` step the calendar via `AddDate` rather than approximating 30/365 days. Both are shared by the HTTP endpoint and the MCP `publish_file` tool. This replaced a fixed preset set (`24h`/`48h`/`72h`/`7d`/`30d`); all five still parse under the grammar, so stored links and existing MCP callers were unaffected.
- `internal/server/server.go` — assembles the chi router:
  - `/api/health`, `/api/setup/status`, `/api/setup`, `/api/auth/{login,register,logout,me}` — public (setup 409s once a user exists; register 403s unless `allow_registration` is on).
  - `/api/files*` (get/create/update/rename/toggle-visibility/tags/expiry/refresh-code/download/soft-delete/restore/hard-delete), `GET /api/search` (own-files substring search, see frontend notes), `DELETE /api/trash` (empty the caller's trash, returns `{deleted}`), `/api/settings` (GET any user / PUT super admin only), `/api/user` (PATCH nickname/password; password changes require the current password), `GET /api/user/usage` (stored bytes + quota), `/api/user/api-key[/reset]` (POST; 409 unless `mcp_enabled`), `/api/backup` (GET download / `POST /api/backup/restore` upload, **super admin only** — the snapshot is the whole DB), `/api/admin/users*` (**super admin only**: `GET` list, `POST` create, `DELETE /{id}`, `PATCH /{id}/status`, `PATCH /{id}/quota`, `POST /{id}/password`) — behind the `requireAuth` middleware, which 401s without a valid credential *and* resolves it to the user, stashing it (plus how they authenticated) in the request context. Two credentials work: the session cookie, and — same key, same rules as `/mcp` — the per-user API key as `Authorization: Bearer rb_...` (dead while `mcp_enabled` is off or the account is suspended; the cookie is tried first). The key is a **file-scope credential**: `requireSuperAdmin` (in `session.go`, the shared preamble of every super-admin handler — settings PUT, backup, `/api/admin/*`) refuses key-authenticated callers even when the key belongs to id=1, because a key that could reach `/api/backup` would reopen the escalation path that makes plaintext `api_key` storage acceptable (see **Users and configs**). `TestAPIKeyCannotUseSuperAdminEndpoints` pins that boundary.
    Handlers behind it call `requireUser(w, r)`; the two routes outside it (`/api/auth/me`, `/res/{slug}`) resolve the credential themselves via `CurrentUser` (so both also accept a Bearer key) — which is also why the identity helpers live in `handlers` rather than `server`, avoiding an import cycle since `server` already imports `handlers`. The `/api/admin/*` handlers re-check super admin individually rather than sitting behind a middleware on that subtree, so mounting one elsewhere by mistake still fails closed.
  - **Nothing static may be mounted at the `/api/files/{slug}` level.** chi matches a static segment before a parameter, so a route like the former `/api/files/search` shadows any file whose custom slug happens to be `search` — that file's own endpoint silently answers with the other handler's response. That is why search lives at `/api/search` and emptying the trash at `/api/trash`; `TestFileEndpointsCoverAllRoutes` walks the router and fails if a static segment reappears there.
  - `/res/{slug}` — the public file-viewing endpoint (`FilesHandler.Render`), which serves every response through `setUserContentHeaders` (see **User content is sandboxed** below), gated by its own logic rather than middleware: 404 if missing, soft-deleted, or owned by a suspended account (all three are "no row" from `GetFileBySlugAnyOwner`, checked *first*, so a valid session can never resurrect a deleted file); else the owner's session bypasses everything; else `is_public` + a `?code=` matching `access_code` (compared with `crypto/subtle.ConstantTimeCompare`) serves it; else 403. Expiry is enforced lazily here (no cron): a public file past its `expires_at` or over its `max_views` is flipped private, its limit columns cleared, and `expired_at`/`expired_reason` (`ttl` or `views`) recorded — only the latest event is kept, and configuring a new limit clears it, so the dashboard badge never contradicts a live expiry. What gets served on success depends on the file's `kind` (see `content.go`), but access control is identical across kinds. The authenticated `/api/files/{slug}/download` returns the untransformed source (not the rendered form) with a kind-appropriate extension/Content-Type. Every access to an existing (non-deleted) file bumps exactly one of `success_count` (the owner), `code_success_count` (a correct access code) or `failure_count` (blocked) — this is analytics, not a content edit, so it deliberately does **not** touch `updated_at`. A 404 for a slug that never existed increments nothing (there's no row to attribute it to).
  - `r.NotFound`/`r.MethodNotAllowed` are registered **on the `/api` subrouter**, not just the root. chi does not inherit a parent's NotFound into a subrouter, so unmatched `/api/*` paths used to fall through to the SPA catch-all and answer `200 text/html`: `fetch()` got HTML where it expected JSON and threw an opaque parse error, and monitoring saw a healthy 200 for a route that does not exist.
  - A `securityHeaders` middleware sets `X-Content-Type-Options: nosniff` and `Referrer-Policy: no-referrer` on everything (the access code rides in the query string, so a referrer leaving the origin would hand it to a third party), plus `X-Frame-Options: DENY` on everything **except** `/res/` — the app's own pages must not be framable, but an owner embedding their own published document is reasonable. It deliberately sets no global CSP: the SPA and uploaded documents want opposite policies.
  - Catch-all SPA handler serving embedded static files, falling back to `index.html` for unknown paths (client-side routing).
- `internal/backup/` — `Snapshot` (VACUUM INTO, streamed straight to the browser) and `Restore`. Restore **copies rows into the existing database** rather than swapping the file: swapping would mean closing the live `*sql.DB` and handing a new one to every handler that captured a `*sqlcgen.Queries` at construction, with a window where the database is simply gone. Instead the snapshot is opened through `db.Open` (which migrates it up to the current schema — that is what makes an older backup restorable), then ATTACHed and copied table by table inside one transaction on one `*sql.Conn`, so a failure rolls back and the live data is untouched. Three things there are load-bearing:
  - **Identifiers are bracket-quoted, not double-quoted.** SQLite's double-quoted-string misfeature degrades `"tags"` to the string literal `'tags'` when no such column exists, so a snapshot missing a column would *silently* copy the column's name into every row instead of failing. Brackets have no such fallback.
  - **The column list is compared between `main` and `restore_src` up front**, so a schema mismatch is reported as `ErrSchemaMismatch` naming the column rather than as a bare "no such column" from mid-copy.
  - **`schema_migrations` is NOT copied.** It records which migrations *this binary* has applied, which is a property of the running code, not of the data. Copying it let a snapshot from a newer build tell an older one that a migration it never ran was already applied — and `db.Open` skips anything already recorded, so that migration would be skipped **forever**, leaving queries referencing a column that does not exist. The live ledger is already correct: the snapshot is opened through `db.Open` and migrated up to this binary's schema before a single row is copied. That sequence (pull, roll back, restore) is the documented rollback path, so this is reachable, not theoretical.
  - **`sqlite_sequence` is copied too.** It holds the highest id ever issued per AUTOINCREMENT table; leaving the live value while replacing the rows under it would let a restore from a larger database hand out ids that already exist.
- `internal/web/` — embeds the built frontend.

To add an endpoint: write the SQL in `internal/db/queries/`, run `make sqlc`, write a handler using the generated `Queries` methods, register the route in `internal/server/server.go`.

**Sessions are DB-backed** (a `sessions` table with a `user_id` column, not an in-memory map) so logins survive process restarts/redeploys — consistent with this app's "all state lives in SQLite/volumes" model. There's no session cleanup cron; expired rows are opportunistically deleted on each login, and `GetValidSession` filters on `unixepoch(expires_at) > unixepoch('now')` so an expired token is never treated as valid even before that sweep runs. `unixepoch()` rather than a text `>`: the column holds an ISO-8601 string and `CURRENT_TIMESTAMP` a bare `YYYY-MM-DD HH:MM:SS`, so comparing them directly is a lexicographic accident (a value it cannot parse yields NULL, which reads as expired — the fail-closed direction). A self-service password change does **not** invalidate existing sessions (they're looked up by token only); an *admin* reset and a suspension both call `DeleteUserSessions`, since those exist for locked-out or compromised accounts. To force every session out, run `DELETE FROM sessions` against the SQLite file.

**Timestamps.** The DSN pins `_time_format=sqlite&_timezone=UTC`, and that is load-bearing. The driver's default write format is Go's `time.Time.String()` — local wall clock with the monotonic clock reading appended (`2026-09-09 09:40:21.365288 +0800 CST m=+2592020.55`) — which nothing else in the database speaks, so every SQL comparison against a `CURRENT_TIMESTAMP` column mixed two formats *and* two time zones. With these set, writes are ISO-8601 UTC and offset-less stored values read back as UTC. Migration 0002 rewrote the rows already written the old way (instant preserved, sub-second precision dropped), so upgrading does not force anyone to log in again; `TestTimestampsStoredAsComparableUTC` and `TestMigrationRewritesLegacyTimestamps` pin both halves.

**User content is sandboxed.** `/res/{slug}` serves uploader-authored HTML verbatim from the same origin as the API, and `Content-Security-Policy: sandbox allow-scripts …` (in `handlers.userContentCSP`) is the whole thing standing between that and account takeover. Omitting `allow-same-origin` is the point: it puts the document in an opaque origin, so a relative `fetch('/api/…')` goes out cross-origin, without cookies, and is refused for lack of CORS headers. `HttpOnly` was never enough — it stops a script *reading* the session cookie, not *using* it, and `SameSite=Lax` has nothing to say about a request that is not cross-site. A document uploaded by one account and opened by another, signed in, ran as that viewer: it could read and delete their files, and against the super admin download the whole database (every hash and API key) or reset their password. That was fine while the only uploader was the person running the server; it stopped being fine when the app grew accounts and a registration toggle, and the reasoning didn't get revisited. The second half of that chain is closed in `AdminHandler.ResetPassword`, which now refuses to target the caller — changing your own password is `PATCH /api/user`, and that requires the current one. Everything a shared document legitimately does still works (scripts, links, forms, popups, downloads), so the sandbox costs the feature nothing. `TestRenderSandboxesUserContent` pins it, including that `allow-same-origin` never reappears.

**Users and configs.** The `users` table holds `username` (unique), `nickname`, `password_hash` (bcrypt), a nullable per-user `api_key` (created lazily when MCP is enabled and the user visits settings; reset always issues a fresh one), a nullable `disabled_at`, and `quota_bytes` (see **Quota** above). The first row is created by `CreateFirstUser`, an `INSERT … WHERE NOT EXISTS (SELECT 1 FROM users)`: the welcome flow used to read `CountUsers`, spend ~80ms hashing, then insert, so six concurrent `POST /api/setup` calls created six accounts — of which only id=1 got the non-transferable super-admin role. Moving the decision into the write makes the loser match no row, which the handler reports as the same 409 a late sequential request already got. The super admin is **id=1 by convention** (`handlers.SuperAdminID`) — the first row created wins, whether via `/api/setup` or a seeded test. The `configs` table is a generic TEXT key/value store; current keys are `allow_registration`, `mcp_enabled` and `upload_default_public` (see **Quota** above for the latter's semantics). `files.user_id` records the uploader (all pre-migration rows were backfilled to user 1) and **every** file path is scoped by it — web, search and MCP alike, with **no super-admin exception** (id=1 only gains the global config toggles and `/api/backup`). **Account suspension** (`disabled_at`) has to close every door, and does it in four places rather than one because there are four ways in: `Login` 403s after the password verifies, `CurrentUser`/`CurrentIdentity` refuses to resolve a session or a REST Bearer key (so suspension takes effect on the very next request of an already-issued credential), `verifyAPIKey` rejects the MCP key, and `GetFileBySlugAnyOwner`'s join takes the account's `/res/{slug}` links offline. The super admin can never be suspended — it is the only account that can lift a suspension, so that would be a one-way door out of the app — and the role is not transferable (id=1 by convention, no endpoint changes it). `api_key` is stored in plaintext; that's a recorded deferral, not an oversight — it stopped being an escalation path once `/api/backup` became super-admin only, and hashing it would force the settings page from "view your key any time" to "shown once at creation", which is a product decision to make on its own. Letting the key call the REST API did not change that calculus **because** `requireSuperAdmin` refuses key-authenticated callers: a leaked key — anyone's, including the super admin's — still cannot reach the backup, the account list, or the global toggles.

**MCP server** (`internal/handlers/mcp.go`, mounted at `/mcp` in server.go — outside `/api` and the session middleware). Built on the official `github.com/modelcontextprotocol/go-sdk` (v1.4.1, pinned; pure Go — a discussed, accepted dependency; v1.2.0 had four vulnerabilities govulncheck reported as reachable, and the bump needed no code changes): stateless streamable HTTP (`Stateless: true, JSONResponse: true`), so every `tools/call` POST is self-contained (no initialize handshake, no session state, GET/DELETE are 405). Layering: `http.MaxBytesReader` cap (at least 32MiB and large enough for one maximally escaped configured-size document; the SDK reads whole messages into memory and has no cap of its own) → `mcp_enabled` config gate (403 when off) → SDK `auth.RequireBearerToken` (imported as `mcpauth`; 401 on bad keys) → MCP server. The verifier resolves the Bearer token via `GetUserByAPIKey` and smuggles the user row plus the share base URL to tool handlers through `TokenInfo.Extra` / `req.Extra.TokenInfo`: `PUBLIC_SHARE_BASE_URL` wins when configured, otherwise the request-derived origin remains `X-Forwarded-Proto`/`-Host` aware. v1.2.0 rejects zero-expiration tokens, so the verifier sets a dummy 1h expiration (keys don't actually expire). Eight typed tools (`mcp.AddTool`, schemas inferred from struct tags; returned errors become tool errors, not protocol errors), all scoped to the key owner's files (`ownedFile` wraps `GetUserFileBySlug`, so a missing slug and a foreign one are literally the same case — no row — and both yield "file not found in this project"): `upload_file`/`upload_files` (markdown/html only — stricter than the web API's `normalizeKind` — created **private**, batch capped at 20, and subject to the configured per-file limit, the owner's quota and `maxNameBytes` exactly as the web API is), `list_files` (the owner's files, newest first, capped at 200 with the true total reported alongside), `search_files` (name+content via `SearchUserFilesWithContent`), `update_file` (name/content only; slug/kind/access-code immutable over MCP), `publish_file` (sets `is_public`, optionally with a `ttl` or `max_views` limit — one `SetFileExpiry` statement, not a visibility write followed by an expiry write that could leave the file public with no limit), `unpublish_file` (visibility only; any expiry limit is left in place so re-publishing resumes the same countdown), `delete_file` (two-phase: without `confirm` it only returns the file's name+URL for the user to confirm; with `confirm=true` it soft-deletes — `HardDeleteFile` is deliberately unreachable over MCP). Upload reuses `createFileWithFreshSlug` (extracted from `FilesHandler.Create`), and `TestMCPToolsAreAllTested` walks `tools/list` so a new tool without a test fails an existing test.

**Frontend layout** (`web/`, SvelteKit 2 + Svelte 5): pure SPA — `ssr` is disabled globally (`src/routes/+layout.ts`), and `@sveltejs/adapter-static` is configured with `fallback: 'index.html'` (see `vite.config.ts`; there is no separate `svelte.config.js` — adapter/compiler options live in the `sveltekit()` vite plugin config). Components use Svelte 5 runes (`$state`, `$props`, etc.) exclusively — no Svelte 4 patterns, no Redux/Zustand-style stores. Directory convention: `src/lib/api/` (fetch wrappers around backend endpoints), `src/lib/schemas/` (zod schemas), `src/lib/components/`, `src/lib/i18n/` (a dependency-free runtime built on one module-scoped `$state` rune: `messages.ts` holds flat `en`/`zh` catalogs where `en` is the key-set source of truth and `zh` is held to it by `satisfies Record<MessageKey, string>`, so a missing translation is a type error; `t()` reads the locale inside templates, which is why switching it re-renders every string with no reload). Forms use `sveltekit-superforms` in **SPA mode** (`superForm(..., { SPA: true, validators: zodClient(schema) })` with the `zod4`/`zod4Client` adapters from `sveltekit-superforms/adapters` — this project uses zod v4, and the plain `zod`/`zodClient` exports from that package are for zod v3) since there's no SvelteKit server to host form actions. Styling is Tailwind v4 (CSS-first config via `@theme` in `src/routes/layout.css`, no `tailwind.config.js`). Icons come from `@iconify/svelte` + `@iconify-json/lucide`; add other icon sets only when a design actually needs them. `src/lib/icons.ts` registers the whole Lucide set into `@iconify/svelte`'s in-memory store via `addCollection` (imported once, as a side effect, from the root `+layout.svelte`) — without it, `<Icon icon="lucide:...">` falls back to fetching from the public Iconify API at runtime, which is wrong for a self-hosted app with no guaranteed internet access. This costs ~90KB gzipped in the root layout chunk; fine at this app's scale — revisit with per-icon subsetting only if that ever actually matters. Fonts are `@fontsource-variable/inter` (sans) and `@fontsource-variable/jetbrains-mono` (mono, used for slugs/HTML source). The whole app is a fixed dark theme (`color-scheme: dark` + `bg-neutral-950` on `body` in `layout.css`) — there's no light-mode toggle.

The root `+layout.ts` is also the auth guard for the whole SPA: it first fetches `/api/setup/status` — while no user exists every route redirects to `/welcome` (the first-run page that creates the super admin and picks the initial `allow_registration`/`mcp_enabled` configs); once set up, `/welcome` redirects to `/login`, `/login` and `/register` stay public, and every other route `fetch('/api/auth/me')`s, redirecting to `/login` on a 401. The guard returns `{ user, allowRegistration }` as layout data — pages read the current user from there rather than re-fetching. `/settings` (linked from the dashboard top bar) is the single administrative surface: profile (nickname + password change, any user), then — super admin only, not rendered at all otherwise — account management and backup/restore, then the registration, default-upload-visibility and MCP toggles (rendered for everyone but disabled for non-super-admins), and — when MCP is on — the per-user API key with copy and a confirm-modal-guarded reset. The two admin sections are route-local components (`settings/AccountsSection.svelte`, `settings/BackupSection.svelte`) rather than `$lib/components/` entries, which is for shared UI; SvelteKit only routes `+`-prefixed files, so a plain component in a route directory is not reachable as a URL. `AccountsSection` renders one row per account with its file counts, its `used / quota` (click to edit inline, in MB), a suspend/restore button, a reset-password modal, an **Add account** modal (which shows the server-generated password once, with a copy button, because nothing stores it in readable form) and a **delete** button behind a modal that names the file count and says the files are erased rather than trashed. Suspend and delete are both disabled on the super admin's row, and the server refuses both independently; `BackupSection` offers the download plus a two-step upload (pick a file, then confirm a warning) and reloads the page 1.5s after a successful restore, since the restored sessions table has most likely signed the admin out and every piece of loaded state is stale. Neither is a top-bar button: the bar stays three items for everyone rather than changing shape by role, and these are rare, consequential operations. Shared UI: `src/lib/components/Toggle.svelte` (controlled switch; the parent flips state only after the API call succeeds). Two dependency-free utility modules sit beside the API wrappers: `src/lib/format.ts` (`formatSize` — largest unit that keeps the number above 1, two decimals, whole bytes under 1KB; `parseSize` — accepts `100`, `500MB`, `1.5 gb`, defaulting a bare number to MB) and **`src/lib/clipboard.ts` (`copyText`), which every copy button must go through**. `navigator.clipboard` only exists in a secure context, and this app is explicitly self-hostable over `http://<lan-ip>`; calling it unguarded there throws into an unhandled rejection, which is exactly how every copy button used to fail — no copy, no error, nothing on screen. `copyText` tries the modern API, falls back to `document.execCommand('copy')`, and *reports* failure so the caller can show the text somewhere selectable (the dashboard renders a read-only, auto-selected input). A deployment behind an HTTPS-terminating proxy is a secure context, so the modern path is what runs in production. `src/routes/+page.svelte` is the file-management dashboard (`+page.ts` preloads the list; the top bar shows the signed-in account's *nickname*, since on a multi-user instance there was otherwise no way to tell which account you were in without opening settings, and the stats block shows `used / quota` from `GET /api/user/usage` — fetched separately because it counts trashed files, matching what the server enforces, so summing the visible rows would show a smaller number than the one that rejects the next upload); it links to `/res/{slug}?code={access_code}` with `target="_blank"` + `data-sveltekit-reload` (that path is served by the Go backend, not a SvelteKit route — same reasoning as the `svelte/no-navigation-without-resolve` eslint-disable next to it). Internal navigations (`goto`) use `resolve()` from `$app/paths` per that same lint rule.

The public/private filter and sort (by name/success-count/failure-count, both directions) are client-side over the already-fetched file list. Search is **not**: the search bar above the list calls `GET /api/search?q=…&content=true|false` (250ms debounce, sequence-numbered so stale responses are dropped), which does a substring search over the *current user's own* non-deleted files — name-only by default, plus `html_content` when the "搜索正文" toggle next to the box is on. A name hit renders as a plain row; a content-only hit also returns a `snippet` (the match ±100 runes, ellipsized, built by `contentSnippet` in `internal/handlers/files.go`) that the row shows as de-emphasized text. Result rows are joined back against the local `files` array (`searchRows`), so optimistic mutations (rename/delete/visibility) reflect immediately; the visibility filter and sort also apply to results, always as a flat list. Picking an explicit sort key drops the default day-grouped ("Today"/"Yesterday"/…) view in favor of a flat sorted list, since grouping by day and sorting by name/counts at the same time isn't a coherent combination; "Recent" is the only mode that groups (and search results never group). The row markup is a `{#snippet fileRow(file, trashed, excerpt?)}` reused by the grouped, flat, and search render paths — extend it there rather than duplicating the `<li>` markup if any path needs to change. Each row shows its stored size (`formatSize(file.size)`, from the server's `content_size` column — the listing carries no content to measure). A row also carries an "offline" badge when the file is private *and* has an `expired_reason`: expiring clears the limit columns, so without that marker the row could only say "private" and the owner had no way to tell a link that ran out from one they made private themselves. It is shown only while the file is still private, since re-publishing by hand makes the note stale (setting a new limit clears it server-side).

Two dashboard actions besides upload: **New** opens a modal (title, format picker, content) that posts to the same create endpoint — the format is chosen only here, since `kind` is fixed at creation, and a successful create clears the search box and visibility filter so the new file isn't hidden by a stale filter and read as a failed create. **Empty trash** appears in the trash tab and `DELETE`s `/api/trash` behind a `confirm()`. **Local mutations must keep both lists in sync.** `trashedFiles` is fetched once and latched behind `trashedLoaded`, so `onDelete` pushes the row into it as well as removing it from `files`; without that, deleting a file *after* visiting the trash left it in neither list and read as a soft delete having destroyed it. The three actions that change stored bytes (create, empty trash, permanent delete) also call `refreshUsage()`, ignoring failures — a stale quota figure is not worth an error banner over the action the user actually asked for. Refreshing a file's access code is behind a `confirm()` too: it invalidates every link already shared, with no undo, and it sits one icon away from delete.

**Deployment**: single `Dockerfile` (multi-stage: node/pnpm build → golang build with `CGO_ENABLED=0` → alpine runtime) and `docker-compose.yml` with one named volume, `db-data` → `/data`, holding `app.db` and its WAL sidecars — mount the directory, never the single file, or `app.db-wal` ends up outside the mount. (There were once `backup-data`/`log-data` volumes reserved for `internal/backup`/`internal/cron`; nothing ever wrote to them — backups stream a `VACUUM INTO` snapshot straight to the browser and logs go to stdout — so they were removed. Re-add them if a cron-driven, writes-to-disk version ever lands.) The compose project `name:` is pinned so the volume name doesn't change when the checkout directory is renamed. `stop_grace_period` is 15s, just above the server's own 10s shutdown deadline. The container binds to `127.0.0.1:8080` only; a host Nginx/Caddy is expected to reverse-proxy to it, and should forward `X-Forwarded-Proto` (plus `X-Forwarded-Host` if it rewrites the origin) so the session cookie gets its `Secure` flag and MCP hands out correct URLs. Plain HTTP on a LAN address works too — it is only less private, not broken. Log rotation is configured on the `json-file` docker logging driver (`max-size`/`max-file`), not in-app. Upgrades are `docker compose pull && docker compose up -d`; all state lives in the volume, and migrations are forward-only, so rolling back to an older image needs a restored backup, not just an older tag.

**Releasing.** Pushing a `vX.Y.Z` tag runs `.github/workflows/release.yml`: verify (same checks as CI) → publish a multi-arch image to `ghcr.io/shawn-bluce/renderbin` and attach static linux amd64/arm64 binaries to a GitHub Release. Nothing is published without a tag. Three things about it are load-bearing:

- **The release tarballs carry no version in their filename** (`renderbin_linux_amd64.tar.gz`, not `renderbin_v0.1.0_linux_amd64.tar.gz`). A versioned name can never be fetched through `/releases/latest/download/`, which is the URL the README tells people to curl — v0.1.0 shipped with that mismatch and the documented quickstart 404'd. The version is stamped into the binary and reported by `/api/health`, which is where it belongs.
- **Both Dockerfile build stages are pinned to `--platform=$BUILDPLATFORM`, and the Go build takes `ARG TARGETARCH`.** So a multi-arch build never runs under QEMU: the frontend is built once (its output is architecture-independent) and the backend cross-compiles for free, since `CGO_ENABLED=0` plus the pure-Go SQLite driver make arm64 just a different `GOARCH`. Verified locally — buildkit reports the second pass as `[linux/arm64->amd64 backend-build]`, i.e. cross-compiling, and only the tiny runtime stage exists per platform. Don't add `setup-qemu-action`; it would make the build an order of magnitude slower for nothing.
- **`docker-compose.yml` deliberately has no `build:` key.** With both `build` and `image`, compose *builds* when the image is missing locally instead of pulling — silently undoing the point of publishing images.
- **The container runs as uid 10001 and `/data` is pre-created with that owner in the image.** Docker copies a named volume's initial ownership from the image directory it shadows, and only when it first creates the volume. A volume created by an older root-running image stays root-owned and the server can't open its database; fix with `docker run --rm -v renderbin_db-data:/data alpine chown -R 10001:10001 /data`.

**Toolchain.** `go.mod` pins `go 1.26.5` — a patch version, deliberately, because 1.26.1 had nine stdlib vulnerabilities `govulncheck` reported as reachable from this code. CI reads the version from `go.mod` (`go-version-file`), so bumping it there is what moves CI, and `GOTOOLCHAIN=auto` makes a local build fetch it. `govulncheck ./...` currently reports zero; keep it that way when adding dependencies.

**Version stamping.** `internal/buildinfo.Version` is set with `-ldflags -X` — by the Git tag in releases, by `git describe` in `make build`, and left as `"dev"` for a plain `go build`. It's read by `/api/health`, the MCP `Implementation`, and the startup log line. `runtime/debug.ReadBuildInfo`'s VCS stamping isn't an option: it needs `.git` in the build context, which `.dockerignore` excludes on purpose.

## Stack decisions to preserve

These were deliberate choices (see git history / original spec) — don't reintroduce the excluded alternatives without discussing it first:
- **Ownership is enforced in SQL, not in Go.** Every file query reachable from `requireAuth` filters on `user_id`, so a foreign slug simply matches no row. Don't "simplify" this into a Go-side check before an unscoped query: `emit_interface: false` means dropping a `user_id` predicate breaks the build at every call site, whereas a forgotten Go check compiles fine. Caveat worth knowing — that guarantee is strong for scalar-arg queries but weaker for `...Params` structs, where a literal may legally omit the new field; `TestFileQueriesRejectForeignOwner` and `TestFileEndpointsCoverAllRoutes` cover that gap.
- **Status codes: 404 when the question is "does this object exist", 403 when it's "may this role use this known, public endpoint".** So a foreign or missing slug is an identical 404 everywhere (slugs are ~24 bits and half the credential for `/res/{slug}?code=`; a 403 would make any account a slug oracle), while `/api/backup` and `PUT /api/settings` answer 403. Known residual: `files.slug` is globally UNIQUE, so renaming onto a stranger's slug still 409s — an existence oracle inherent to a global slug namespace, accepted rather than fixed.
- No ORM (GORM/ent) — sqlc-generated code + raw SQL only.
- No CGO SQLite driver — `modernc.org/sqlite` only, so cross-compilation and the alpine runtime stay simple.
- Markdown rendering is `github.com/yuin/goldmark` (pure Go, no CGO — consistent with the SQLite-driver choice). Don't swap in a CGO-based renderer (e.g. cmark bindings). Rendering happens server-side in `Render`; there's no client-side markdown library.
- No Redux/Zustand-equivalent frontend state library — Svelte 5 runes only.
- No microservices, no message queue, no Redis/cache layer.
- Auth is hand-rolled on `golang.org/x/crypto` (bcrypt), not a third-party auth service — users live in the `users` table (no env-var credentials; don't reintroduce `ADMIN_USERNAME`/`ADMIN_PASSWORD`), the super admin is id=1 by convention, and registration is gated by the `allow_registration` config. Recovery is **the super admin resetting the password for you** (`POST /api/admin/users/{id}/password`), deliberately instead of a self-service "forgot password" flow: that would need email, which this app has no business owning. Don't add email verification, roles beyond the id=1 super admin plus `disabled_at`, or login rate-limiting without discussing it first; these were explicitly scoped out (bcrypt's own per-attempt cost is the accepted mitigation for no rate-limiting). No CSRF token either — `SameSite=Lax` on the session cookie is the accepted mitigation.
- **API keys are file-scope credentials; only a session unlocks super-admin power.** A Bearer key authenticates the REST API and MCP alike, but every super-admin handler goes through `requireSuperAdmin`, which refuses key auth — that boundary is what keeps plaintext `api_key` storage an acceptable deferral. New super-admin endpoints must use `requireSuperAdmin`, never a bare `IsSuperAdmin` check after `requireUser`.
- **User-uploaded content is sandboxed by CSP, not sanitized.** Don't drop the `Content-Security-Policy: sandbox` header from `/res/{slug}`, and above all don't add `allow-same-origin` to it — see **User content is sandboxed** above for what that costs. Sanitizing the HTML instead is the wrong trade in the other direction: serving authored HTML verbatim *is* the product. Serving `/res` from a separate hostname is the stronger version of the same fix and is the thing to reach for if the sandbox ever proves too tight.
- **Account limits are enforced per account, not per protocol.** Quota and name bounds apply on the MCP path as well as the HTTP one. Anything new that stores content must call `enforceQuota`.
- **Every JSON endpoint caps its request body.** Don't call `json.NewDecoder(r.Body).Decode` directly in a handler; use `decodeSmallJSON`/`decodeJSON`. `encoding/json` buffers the whole value, so an uncapped decode is a one-request OOM on the small VPS this app is meant to run on.
- **The session cookie's `Secure` flag follows the request's scheme.** Don't "harden" it back to a constant `true`: a browser discards a Secure cookie that arrives over plain HTTP from anything but localhost, so that turns self-hosting over `http://<lan-ip>` into a login that silently never takes. `TestSessionCookieSecureFollowsScheme` covers all three deployments (localhost, LAN, HTTPS proxy).
- **Restoring a backup copies rows into the live database; it does not swap the file or restart the process.** Don't "simplify" it into a file swap — see `internal/backup` above for what that would cost. Equally, don't relax the bracket quoting or the column-set check: both exist because the failure they prevent writes wrong data instead of erroring.
- **Storage is limited per account, not globally.** `users.quota_bytes` defaults to 100MB and the super admin can change it per account. Don't reintroduce an unbounded upload path: with registration on, one stranger filled 160MB in 1.4 seconds before this existed, and the whole app is a single SQLite file on a volume that a full disk takes down.
- `internal/cron` and `internal/ratelimit` are still-reserved package names for functionality to add as needed (`internal/auth` and `internal/backup` are implemented) — don't invent different locations for that logic later. The trash deliberately has no auto-purge cron; "empty trash" is a user action.
